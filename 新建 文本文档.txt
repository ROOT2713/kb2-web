## 1. 概述

### 1.1 文档目的与版本说明

本文档整合了《kb2-web 知识库系统演进方案综合评估》（2026-07-01）、kb2-web v2 公开仓库实际代码审查、以及链路实效优化审阅意见，形成最终可落地的实施指南。

**v3.1 相对 v3.0 的关键变更**：

| 变更项 | 说明 |
|--------|------|
| 新增 Phase 0 | CI 评估器去抖、异步任务状态机、成本监控基础——作为 Phase 1 启动的前置条件 |
| OKF 收益细化评估 | 从“模块完成度”转为“链路实效收益”量化分析，识别真正的瓶颈 |
| 7 阶段 SOP 异步化 | 禁止重操作阻塞同步链路，采用 SQLite 任务状态机 + BackgroundTasks |
| 66 题 CI 评估器去抖 | 规则优先 + LLM 3 次取众数，连续 3 次下降趋势才阻塞 |
| GraphRAG 消融实验决策门 | Phase 2 第 1 周必须完成离线增益验证，< 5% 则暂停并转投其他方向 |
| 成本-收益实时监控 | admin.py 增加 Token 消耗与成本统计，按 API 分账 |
| SourceCard 证据级可解释性 | 命中词高亮 + 费用档位标签，替代单纯堆砌字段 |
| 多轮对话知识域锚定 | 利用 query_decomposer 检测 domain 跨越并重置检索域 |

### 1.2 核心结论

经过对代码仓库（48 个后端文件、374 测试用例、25 个 API 端点）的全面审查，得出以下判断：

1. **项目基础扎实但存在链路断裂**：OKF 核心模块（concept 生成、质量门禁、过时检测、图谱遍历）大多已实现，但它们彼此孤立，未形成从上传到检索的完整信息链。
2. **OKF 的真正瓶颈不是功能缺失，而是“同步阻塞”和“无兜底机制”**：上传接口同步执行重解析会阻塞 Worker，concept 自动生成无人工复核会被 LLM 幻觉污染数据。
3. **GraphRAG 的收益在政务强事实场景下高度不确定**：必须在投入 3 周前完成消融实验。若增益 < 5%，应果断裁剪并将资源转向深化 fee_utils 或同义词扩展。
4. **评估体系的稳定性是全部验收的前提**：LLM 评分方差会导致 CI 频繁误报，必须先校准评估器再推进任何功能开发。

### 1.3 方案依赖关系与铁律

```
        C: 前端重构 (交互表现层)
┌─────────────────────────────────┐
│   A: GraphRAG (智能检索层)      │
│ ┌───────────────────────────┐   │
│ │ B: OKF 信息架构(数据底座) │   │
│ └───────────────────────────┘   │
└─────────────────────────────────┘
```

**铁律（不可违反）**：
- B 未定型前，A 的实体类型设计不能启动  
- A 的检索 API 契约未冻结前，C 的 P2 查询工作台不能重构  
- **新增**：CI 评估器未校准前，任何 Phase 的验收标准不能生效  
- **新增**：GraphRAG 消融实验增益 < 5% 时，Phase 2 剩余内容必须重定向

**关键判断**：OKF 的模块级完成度（~50%）与链路就绪度（~15%）之间存在巨大鸿沟。真正的瓶颈不是开发新功能，而是完成三项集成工作：
1. concept/document 关联（数据库 + 迁移）
2. 上传管线流程编排（含异步化）
3. 域路由规则落地

#### 2.2.2 链路实效收益量化评估

以下分析基于“每个 OKF 能力投入生产后，对核心指标（66 题通过率、用户采信率、系统稳定性）的预期提升”：

| OKF 能力 | 预期收益 | 收益确定性 | 风险 | 优先级判断 |
|----------|---------|-----------|------|-----------|
| **domain 路由** | 66 题通过率 +3-5pp（减少跨域噪音） | 中高 | 路由错误导致召回丢失（需兜底） | **P1** |
| **concept_id 关联** | 间接收益（为 GraphRAG、版本链提供外键） | 高 | 迁移过程可能导致短期波动 | **P1** |
| **7 阶段 SOP 异步化** | 系统稳定性从“不可靠”到“可靠”（上传不再阻塞） | **极高** | 无（纯工程改进） | **P0** |
| **质量门禁 G1-G3** | 阻断劣质文档入库，长期提升检索质量 | 中（长期见效） | 门禁过严会拒收有效文档 | **P1** |
| **过时检测联动检索** | 66 题通过率 +1-2pp（减少过期文档污染） | 中 | 误判过期会导致有效文档被降权 | **P2** |
| **版本链** | 间接收益（用户可感知标准替代关系） | 低（当前文档量少，版本冲突不突出） | 低 | **P2** |
| **置信度兜底** | 防止 LLM 幻觉污染数据底座 | **极高** | 无（纯防御性机制） | **P0** |

**核心结论**：
- **OKF 方案对 66 题通过率的直接提升有限（预计 +3-5pp）**，其主要价值是**为后续 GraphRAG 和版本链提供数据基础**，以及**通过异步化保障系统稳定性**。
- 如果将“66 题通过率提升”作为唯一衡量标准，OKF 的 2 周投入性价比中等。但如果将“系统稳定性”和“数据底座可扩展性”纳入考量，则 OKF 是**不可跳过的基础设施投资**。
- **7 阶段 SOP 异步化**和**置信度兜底**是 ROI 最高的两项 OKF 子任务——前者解决生产级稳定性，后者用最小代价防止垃圾数据污染。

## 3. 三套方案深度分析

### 3.1 B 方案：OKF 信息架构

**目标**：从扁平的 bank 结构迁移到 6 大语义顶域，建立 concept_id 体系，标准化并异步化文档入库流程。

**收益重估后实施策略**：
- **异步化优先**：7 阶段 SOP 中的解析、Chunking、实体抽取全部移出同步链路，通过 SQLite 任务状态机 + FastAPI BackgroundTasks 执行。上传接口立即返回 task_id，前端轮询进度。
- **用“关联”代替“重建”**：利用已有的 `concept_gen.py` 批量生成 concept 并回填到 `documents` 表新增字段。
- **兜底机制必建**：调用 `confidence.py` 对自动生成 concept 打分，< 0.8 标记为 `human_review_required=true`，降级使用原 bank 路由。
- **域路由采用推断+缓存模式**：根据文档标题、关键词、bank 来源自动推断 domain，写入 `documents.domain`。

### 3.2 A 方案：GraphRAG 图谱检索

**目标**：让系统理解文档间的引用关系，在检索时提升关联类问题的召回。

**关键修正——消融实验决策门**：
- **在 Phase 2 投入 3 周前，必须先完成 1 周的离线增益验证**。从 66 题中抽取所有关联引用类问题，手工标注 10-20 条真实三元组，对比加入图谱遍历前后的召回准确率增量。
- **若增益 < 5%，触发红线**：暂停 GraphRAG 主链路集成，将 Phase 2 剩余 2 周资源转向深化 `fee_utils` 或同义词扩展。
- **关系抽取策略**：优先利用 `frontmatter.py` 解析 Markdown 引用链接和 YAML `references` 字段生成 KGTriple；正则扫描正文作为补充；不使用 LLM 抽取。

### 3.3 C 方案：前端重构

**目标**：从“AI 塑料感”进化为专业化知识库交互界面。

**关键修正**：
- **P0 不止换肤**：`SourceCard.vue` 必须升级为“证据级可解释性”——展示命中 BM25 关键词高亮、`fee_utils` 档位标签、图谱关联路径缩略图。
- **P2 多轮对话**：利用 `query_decomposer.py` 检测 domain 跨越，强制切换检索域并给 UI 提示，防止上下文漂移。

### 4.2 Phase 0：工程前提（本周，2-3 天）

**入口条件**：当前 main 分支稳定，74.2% 基线锁定。

#### 任务 0.1：CI 评估器去抖（最高优先级，D1）

**问题**：LLM 单次评分方差大，作为 CI 硬拦截会产生 Flaky Build，严重阻塞团队开发流。

**方案**：
- **确定题型规则严格匹配**：对取费金额、标准号等有确定答案的题型，在 `kb2_66test_v3.py` 中增加规则匹配函数，答案命中目标关键词即 PASS，不走 LLM。
- **开放题型 LLM 3 次取众数**：对开放性问答，调用 LLM 评估 3 次，2/3 一致即为最终判定。3 次均不一致标记为 `UNCERTAIN`，转人工复核。
- **CI 阻塞规则改为趋势告警**：不因单次下降 2pp 阻塞 PR。改为：连续 3 次 commit 的 66 题通过率呈下降趋势（每次降幅 ≥1pp），才触发阻塞。

**产出**：`backend/scripts/kb2_66test_v3.py` 更新版 + CI 配置更新

#### 任务 0.2：异步任务状态机设计（D1-D2）

**问题**：当前 `upload.py` 中解析、Chunking 等重操作在请求同步链路中执行，大文件会导致 HTTP 超时及 FastAPI Worker 阻塞。

**方案**：
- 在 `backend/app/models/` 中新增 `UploadTask` 模型（SQLite 表）：
```python
class UploadTask(Base):
    __tablename__ = "upload_tasks"
    id: str          # UUID
    status: str      # pending/processing/done/failed
    filename: str
    progress: float  # 0.0 - 1.0
    stage: str       # 当前阶段名称
    error_message: Optional[str]
    result_doc_id: Optional[str]
    created_at: datetime
    updated_at: datetime
```
- 上传接口重构：`POST /api/upload` 立即返回 `{"task_id": "uuid", "status": "pending"}`，后台通过 FastAPI `BackgroundTasks` 执行 Stage 0-6。
- 新增 `GET /api/upload/tasks/{task_id}` 接口，返回任务状态和进度，供前端轮询。

**产出**：Alembic migration + `UploadTask` 模型 + 上传接口重构

#### 任务 0.3：成本监控看板骨架（D2）

**问题**：引入多轮对话、GraphRAG 后 LLM 调用频次指数级上升，缺乏监控会导致 API 账单失控。

**方案**：
- 在 `backend/app/services/` 中新增 `cost_tracker.py`，拦截所有 LLM 调用（生成、Rerank、抽取），记录 Token 用量和对应成本（基于 DeepSeek V4 定价）。
- 在 `admin.py` 统计面板中增加“今日/本周/本月 Token 消耗与费用”API。
- 前端 `AdminView.vue` 增加成本趋势图。

**产出**：`cost_tracker.py` + `admin.py` 新接口 + 前端成本卡片

**Phase 1 验收标准**：
- 异步上传接口响应 < 200ms，支持大文件无超时

### 8.3 C. GraphRAG 离线消融实验方案

**目的**：验证在政务强事实场景下，图谱遍历对检索效果的增量价值。

**步骤**：
1. **抽取测试子集**：从 66 题中筛选关联引用类问题（如“GB 50174 引用了哪个标准”“等保管理办法的上级文件是什么”），预计 10-15 题。
2. **手工标注三元组**：从已有 140 篇文档中，找出与测试子集相关的文档，手工标注 10-20 条真实引用关系，写入 `kg_triples` 表。
3. **建立基线**：运行 `kb2_66test_v3.py`（校准版），记录测试子集的通过率作为基线。
4. **临时集成**：在 `retrieval.py` 中增加条件分支，当配置 `GRAPHRAG_ABLATION_MODE=true` 时启用图谱遍历结果（权重 0.3），否则仅 BM25+Hindsight。
5. **A/B 对比**：分别运行基线模式和增强模式，对比测试子集通过率。
6. **性能测量**：分别测量两种模式的 P95 检索延迟。

**决策**：
| 结果 | 决策 |
|------|------|
| 通过率提升 ≥ 5% 且延迟增加 ≤ 30% | **Go**：继续推进 |
| 否则 | **No-Go**：暂停，资源重定向 |

## 1. 概述

### 1.1 文档目的与版本说明

本文档整合了《kb2-web 知识库系统演进方案综合评估》（2026-07-01）、kb2-web v2 公开仓库实际代码审查、以及链路实效优化审阅意见，形成最终可落地的实施指南。

**v3.1 相对 v3.0 的关键变更**：

| 变更项 | 说明 |
|--------|------|
| 新增 Phase 0 | CI 评估器去抖、异步任务状态机、成本监控基础——作为 Phase 1 启动的前置条件 |
| OKF 收益细化评估 | 从“模块完成度”转为“链路实效收益”量化分析，识别真正的瓶颈 |

| 多轮对话知识域锚定 | 利用 query_decomposer 检测 domain 跨越并重置检索域 |

### 1.2 核心结论

经过对代码仓库（48 个后端文件、374 测试用例、25 个 API 端点）的全面审查，得出以下判断：

1. **项目基础扎实但存在链路断裂**：OKF 核心模块（concept 生成、质量门禁、过时检测、图谱遍历）大多已实现，但它们彼此孤立，未形成从上传到检索的完整信息链。
2. **OKF 的真正瓶颈不是功能缺失，而是“同步阻塞”和“无兜底机制”**：上传接口同步执行重解析会阻塞 Worker，concept 自动生成无人工复核会被 LLM 幻觉污染数据。
3. **GraphRAG 的收益在政务强事实场景下高度不确定**：必须在投入 3 周前完成消融实验。若增益 < 5%，应果断裁剪并将资源转向深化 fee_utils 或同义词扩展。
4. **评估体系的稳定性是全部验收的前提**：LLM 评分方差会导致 CI 频繁误报，必须先校准评估器再推进任何功能开发。

### 1.3 方案依赖关系与铁律

```
        C: 前端重构 (交互表现层)
┌─────────────────────────────────┐
│   A: GraphRAG (智能检索层)      │
│ ┌───────────────────────────┐   │
│ │ B: OKF 信息架构(数据底座) │   │
│ └───────────────────────────┘   │
└─────────────────────────────────┘
```

**铁律（不可违反）**：
- B 未定型前，A 的实体类型设计不能启动  
- A 的检索 API 契约未冻结前，C 的 P2 查询工作台不能重构  
- **新增**：CI 评估器未校准前，任何 Phase 的验收标准不能生效  
- **新增**：GraphRAG 消融实验增益 < 5% 时，Phase 2 剩余内容必须重定向

| 置信度 | `confidence.py` | 90% | **40%** | 计算逻辑完善，但未与迁移流程的兜底机制绑定 |
| 矛盾精判 | `crystallization_light.py` | 85% | 50% | 功能独立，可在生成环节调用 |
| 图谱遍历 | `graph_traversal.py` | 80% | **0%** | 未接入 `retrieval.py` 的 RRF 融合 |
| KGTriple 表 | `concept.py` | 100% | **0%** | 表结构完备，数据填充量和质量未知 |
| 6 大顶域路由 | — | 0% | 0% | 无代码，仅有 Wiki 设计文档 |

**关键判断**：OKF 的模块级完成度（~50%）与链路就绪度（~15%）之间存在巨大鸿沟。真正的瓶颈不是开发新功能，而是完成三项集成工作：
1. concept/document 关联（数据库 + 迁移）
2. 上传管线流程编排（含异步化）
3. 域路由规则落地

#### 2.2.2 链路实效收益量化评估

以下分析基于“每个 OKF 能力投入生产后，对核心指标（66 题通过率、用户采信率、系统稳定性）的预期提升”：

| OKF 能力 | 预期收益 | 收益确定性 | 风险 | 优先级判断 |
|----------|---------|-----------|------|-----------|
| **domain 路由** | 66 题通过率 +3-5pp（减少跨域噪音） | 中高 | 路由错误导致召回丢失（需兜底） | **P1** |
| **concept_id 关联** | 间接收益（为 GraphRAG、版本链提供外键） | 高 | 迁移过程可能导致短期波动 | **P1** |
| **7 阶段 SOP 异步化** | 系统稳定性从“不可靠”到“可靠”（上传不再阻塞） | **极高** | 无（纯工程改进） | **P0** |
| **质量门禁 G1-G3** | 阻断劣质文档入库，长期提升检索质量 | 中（长期见效） | 门禁过严会拒收有效文档 | **P1** |
| **过时检测联动检索** | 66 题通过率 +1-2pp（减少过期文档污染） | 中 | 误判过期会导致有效文档被降权 | **P2** |
| **版本链** | 间接收益（用户可感知标准替代关系） | 低（当前文档量少，版本冲突不突出） | 低 | **P2** |
| **置信度兜底** | 防止 LLM 幻觉污染数据底座 | **极高** | 无（纯防御性机制） | **P0** |

**核心结论**：
- **OKF 方案对 66 题通过率的直接提升有限（预计 +3-5pp）**，其主要价值是**为后续 GraphRAG 和版本链提供数据基础**，以及**通过异步化保障系统稳定性**。
- 如果将“66 题通过率提升”作为唯一衡量标准，OKF 的 2 周投入性价比中等。但如果将“系统稳定性”和“数据底座可扩展性”纳入考量，则 OKF 是**不可跳过的基础设施投资**。
- **7 阶段 SOP 异步化**和**置信度兜底**是 ROI 最高的两项 OKF 子任务——前者解决生产级稳定性，后者用最小代价防止垃圾数据污染。

## 3. 三套方案深度分析

### 3.1 B 方案：OKF 信息架构

**目标**：从扁平的 bank 结构迁移到 6 大语义顶域，建立 concept_id 体系，标准化并异步化文档入库流程。

**收益重估后实施策略**：
- **异步化优先**：7 阶段 SOP 中的解析、Chunking、实体抽取全部移出同步链路，通过 SQLite 任务状态机 + FastAPI BackgroundTasks 执行。上传接口立即返回 task_id，前端轮询进度。
- **用“关联”代替“重建”**：利用已有的 `concept_gen.py` 批量生成 concept 并回填到 `documents` 表新增字段。
- **兜底机制必建**：调用 `confidence.py` 对自动生成 concept 打分，< 0.8 标记为 `human_review_required=true`，降级使用原 bank 路由。
- **域路由采用推断+缓存模式**：根据文档标题、关键词、bank 来源自动推断 domain，写入 `documents.domain`。

### 3.2 A 方案：GraphRAG 图谱检索

**目标**：让系统理解文档间的引用关系，在检索时提升关联类问题的召回。

**关键修正——消融实验决策门**：
- **在 Phase 2 投入 3 周前，必须先完成 1 周的离线增益验证**。从 66 题中抽取所有关联引用类问题，手工标注 10-20 条真实三元组，对比加入图谱遍历前后的召回准确率增量。
- **若增益 < 5%，触发红线**：暂停 GraphRAG 主链路集成，将 Phase 2 剩余 2 周资源转向深化 `fee_utils` 或同义词扩展。
- **关系抽取策略**：优先利用 `frontmatter.py` 解析 Markdown 引用链接和 YAML `references` 字段生成 KGTriple；正则扫描正文作为补充；不使用 LLM 抽取。

### 3.3 C 方案：前端重构

**目标**：从“AI 塑料感”进化为专业化知识库交互界面。

**关键修正**：
- **P0 不止换肤**：`SourceCard.vue` 必须升级为“证据级可解释性”——展示命中 BM25 关键词高亮、`fee_utils` 档位标签、图谱关联路径缩略图。
- **P2 多轮对话**：利用 `query_decomposer.py` 检测 domain 跨越，强制切换检索域并给 UI 提示，防止上下文漂移。

### 4.2 Phase 0：工程前提（本周，2-3 天）

**入口条件**：当前 main 分支稳定，74.2% 基线锁定。

#### 任务 0.1：CI 评估器去抖（最高优先级，D1）

**问题**：LLM 单次评分方差大，作为 CI 硬拦截会产生 Flaky Build，严重阻塞团队开发流。

**方案**：
- **确定题型规则严格匹配**：对取费金额、标准号等有确定答案的题型，在 `kb2_66test_v3.py` 中增加规则匹配函数，答案命中目标关键词即 PASS，不走 LLM。
- **开放题型 LLM 3 次取众数**：对开放性问答，调用 LLM 评估 3 次，2/3 一致即为最终判定。3 次均不一致标记为 `UNCERTAIN`，转人工复核。
- **CI 阻塞规则改为趋势告警**：不因单次下降 2pp 阻塞 PR。改为：连续 3 次 commit 的 66 题通过率呈下降趋势（每次降幅 ≥1pp），才触发阻塞。

**产出**：`backend/scripts/kb2_66test_v3.py` 更新版 + CI 配置更新

#### 任务 0.2：异步任务状态机设计（D1-D2）

**问题**：当前 `upload.py` 中解析、Chunking 等重操作在请求同步链路中执行，大文件会导致 HTTP 超时及 FastAPI Worker 阻塞。

**方案**：
- 在 `backend/app/models/` 中新增 `UploadTask` 模型（SQLite 表）：
```python
class UploadTask(Base):
    __tablename__ = "upload_tasks"
    id: str          # UUID
    status: str      # pending/processing/done/failed
    filename: str
    progress: float  # 0.0 - 1.0
    stage: str       # 当前阶段名称
    error_message: Optional[str]
    result_doc_id: Optional[str]
    created_at: datetime
    updated_at: datetime
```
- 上传接口重构：`POST /api/upload` 立即返回 `{"task_id": "uuid", "status": "pending"}`，后台通过 FastAPI `BackgroundTasks` 执行 Stage 0-6。
- 新增 `GET /api/upload/tasks/{task_id}` 接口，返回任务状态和进度，供前端轮询。

**产出**：Alembic migration + `UploadTask` 模型 + 上传接口重构

#### 任务 0.3：成本监控看板骨架（D2）

**问题**：引入多轮对话、GraphRAG 后 LLM 调用频次指数级上升，缺乏监控会导致 API 账单失控。

**方案**：
- 在 `backend/app/services/` 中新增 `cost_tracker.py`，拦截所有 LLM 调用（生成、Rerank、抽取），记录 Token 用量和对应成本（基于 DeepSeek V4 定价）。
- 在 `admin.py` 统计面板中增加“今日/本周/本月 Token 消耗与费用”API。
- 前端 `AdminView.vue` 增加成本趋势图。

**产出**：`cost_tracker.py` + `admin.py` 新接口 + 前端成本卡片

### 8.3 C. GraphRAG 离线消融实验方案

**目的**：验证在政务强事实场景下，图谱遍历对检索效果的增量价值。

**步骤**：
1. **抽取测试子集**：从 66 题中筛选关联引用类问题（如“GB 50174 引用了哪个标准”“等保管理办法的上级文件是什么”），预计 10-15 题。
2. **手工标注三元组**：从已有 140 篇文档中，找出与测试子集相关的文档，手工标注 10-20 条真实引用关系，写入 `kg_triples` 表。
3. **建立基线**：运行 `kb2_66test_v3.py`（校准版），记录测试子集的通过率作为基线。
4. **临时集成**：在 `retrieval.py` 中增加条件分支，当配置 `GRAPHRAG_ABLATION_MODE=true` 时启用图谱遍历结果（权重 0.3），否则仅 BM25+Hindsight。
5. **A/B 对比**：分别运行基线模式和增强模式，对比测试子集通过率。
6. **性能测量**：分别测量两种模式的 P95 检索延迟。

**决策**：
| 结果 | 决策 |
|------|------|
| 通过率提升 ≥ 5% 且延迟增加 ≤ 30% | **Go**：继续推进 |
| 否则 | **No-Go**：暂停，资源重定向 |

### 8.5 E. 成本监控看板设计

**数据模型**：
```sql
CREATE TABLE llm_cost_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    api_type TEXT NOT NULL,       -- 'generation' / 'rerank' / 'extraction'
    model TEXT NOT NULL,          -- 'deepseek-chat'
    prompt_tokens INTEGER,
    completion_tokens INTEGER,
    cost_usd REAL,
    endpoint TEXT,                -- 调用来源
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**管理面板 API**：
- `GET /api/admin/cost/today` — 今日消耗
- `GET /api/admin/cost/weekly` — 本周消耗趋势
- `GET /api/admin/cost/by-api` — 按 API 类型分账

**告警规则**：
- 单日消耗超过周预算 30% → 管理员通知
- 单次查询 Token 超过 `LLM_MAX_TOKENS_PER_QUERY` → 记录警告
